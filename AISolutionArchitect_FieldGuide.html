The AI Solution Architect Field Guide

This is the culminating package of the Colaberry Enterprise AI Leadership Accelerator. Eleven weeks taught Business Analysis, Solution Architecture, Project Management, Software Engineering, UX, QA, Integration, AI Engineering, Data Engineering, DevOps, and Governance as separate disciplines. This week teaches the ~20% an AI Solution Architect actually needs to sit above all eleven — not to do their jobs, but to direct, evaluate, and approve the work of an AI-assisted team building a real initiative.

What this is

A working knowledge base, not a slide deck. A left-hand topic nav, a full-text search box, and an offline Q&A assistant that answers from the guide's own content — no external API, works with the file open locally in any browser.

Foundations · 01

The architect's synthesis role

Ten other disciplines each optimize a slice of the system: the Business Analyst optimizes for requirements fidelity, the Software Engineer for build quality, the QA lead for defect escape rate, DevOps for operability, Governance for compliance exposure. Each of those optimizations is locally correct and can still add up to a system that doesn't fit together — a UX flow that assumes synchronous data the Data Engineer built as batch, an AI Engineering approach that assumes latency budgets DevOps never provisioned for.

The Solution Architect's job is synthesis, not authorship: read every upstream artifact, hold the whole system in view, and make the calls that only make sense with that whole-system context — which trade-offs to accept, which risks to escalate, which decisions need to be written down so nobody re-litigates them later. The architect does not write the BRD, the test plan, or the CI/CD pipeline. The architect is accountable for whether all of those pieces, taken together, actually work, ship safely, and stay governable.

In an AI-assisted team When a coding agent (Claude Code or similar) can generate a service, a test suite, or a Terraform module in minutes, the bottleneck stops being "can we build this" and becomes "should we build this, this way, and how do we know it's right." That judgment layer — direct, evaluate, approve — is the architect's ~20%. Everything else in this guide operationalizes that judgment so it's repeatable and defensible, not vibes.

Three questions the architect keeps asking

QuestionWhy it's the architect's, not another discipline's
Does this design still satisfy the original business requirement?The BA wrote the requirement; the architect is the one checking every downstream translation of it stayed faithful across five more disciplines.
What happens when this fails, and who is accountable for that path?Individual services define their own failure handling; only the architect sees whether failure in one service silently breaks an assumption in another.
Is this decision reversible, and did we write down why we made it?No single discipline owns the decision log — it is inherently cross-cutting, which makes it architecture's to keep.
Foundations · 02

End-to-end traceability

A requirement that cannot be traced to a design decision, a build artifact, a test, a runtime control, and a governance rule is a requirement nobody can prove was actually delivered. Traceability is the spine that lets an architect answer "did we build what was asked, and can we prove it" without re-reading every artifact from scratch.

Traceable hand-offGovernance checkpoint (audit-critical)

In practice this means: every row in the Document-Set Index & Traceability ties one requirement ID to a design section, a build artifact (repo path, service name), a test case ID, a runbook or monitoring dashboard, and a governance control. If any link in that chain is blank, the requirement is not done — it is merely built.

Common failure mode Teams trace requirement → design → build well, then stop. The run and govern columns get treated as afterthoughts. That is exactly backwards for AI features: the governance and runtime-monitoring links are where model drift, bias, and compliance exposure actually surface — months after build, not during it.
Foundations · 03

ADRs & the decision log

An Architecture Decision Record (ADR) captures one significant, hard-to-reverse decision: the context that forced it, the options seriously considered, the decision made, and the consequences accepted. The discipline is not the template — it's writing the record before memory of the losing options fades, so a reviewer six months later can see the decision was reasoned, not assumed.

ADR anatomy used throughout this guide

FieldContents
ContextThe forcing constraint — a deadline, a cost ceiling, a compliance requirement, a technical limitation.
Options consideredEvery option seriously evaluated, each with its real trade-off — not a straw-man list built to make the chosen option look inevitable.
DecisionThe option chosen, in one sentence, with no hedging.
ConsequencesWhat we gave up by choosing this — the cost of the decision, stated honestly, plus what would trigger revisiting it.

The decision log is not a single-phase artifact. It runs the whole arc: a BA-phase decision to scope out a feature, a UX-phase decision to skip a device class, a DevOps-phase decision to accept a single-region deployment — all belong in the same log as the architecture-phase decisions, because they all constrain the system the same way. See Document 2 — the Architecture Decision Log for eight real ADRs from the ClaimSight AI initiative, each showing the options it beat.

Foundations · 04

Whole-system trade-offs

Every non-trivial architecture decision trades along at least four axes: cost, latency, risk, and build-vs-buy speed-to-market. A decision that looks obviously correct on one axis is rarely obviously correct on all four — the architect's job is to make the trade explicit, name a winner, and state what was given up, rather than pretending the "best" option wins on every axis simultaneously.

Illustrative trade-off matrix — AI damage-estimation approach

Winning column — see ADR-001 in the Decision Log

The generic method: (1) list the axes that actually matter for this decision — not a fixed universal four — (2) score each option honestly, including the option currently in production if replacing it, (3) name the winner per axis, (4) pick the overall winner and write the ADR explaining why the axes that mattered most outweighed the ones that didn't. A trade-off analysis that produces no losers on any axis is not a trade-off — it's marketing.

Foundations · 05

The architecture package as single source of truth

Eleven disciplines producing eleven independent documents creates eleven independent opinions about what the system is. The architecture package is the mechanism that resolves that: it doesn't replace the BRD, the test strategy, or the runbooks — it indexes and reconciles them into one coherent statement of what the system is, why, and how each discipline's artifact fits.

Foundations · 06

C4 views & quality attributes

The C4 model gives four zoom levels — Context (system + external actors), Container (deployable units inside the system), Component (structures inside one container), and Code (classes — usually left to Engineering). An architect owns Context and Container fully, and reviews Component views for consistency without necessarily drawing them. Document 1 below includes worked Context and Container diagrams for ClaimSight AI.

Quality attribute catalog (the NFR checklist)

Performancep50 / p95 / p99 latency targets per critical path

AvailabilityUptime target, RTO, RPO, and the failure domains that can't take the whole system down together

A design review that never asks "what's the number" on these attributes is not reviewing architecture — it's reviewing a diagram.

Foundations · 07

Cost models & delivery roadmaps

A defensible cost model separates build (one-time, capitalized) from run (recurring, expensed) and expresses the run cost as a unit economic — cost per claim, per prediction, per API call — because unit economics survive volume changes; a flat monthly number does not. A defensible roadmap sequences work by dependency, not by convenience, and gates every phase transition on an explicit approval, not a calendar date slipping past unnoticed. Both are covered in full, with real numbers, in Document 4 and Document 5.

Foundations · 08

Presenting & defending a design

A design review is not a walkthrough — it's a pressure test. Structure the presentation to survive it:

  1. Business framing first. One sentence on the problem and the number that matters (cycle time, cost, revenue) before any diagram appears.
  2. Context, then container. Zoom out before zooming in — a reviewer who doesn't see the boundary of the system will misjudge every internal decision.
  3. Lead with the decisions that could sink the project, not the ones that are easiest to explain. Bury the safe decisions; open with the risky ones you're most confident in.
  4. State the trade-off, not just the choice. "We chose X" invites re-litigation. "We chose X over Y because of Z, and we accept that this costs us W" closes the loop.
  5. Bring the cost and the roadmap. A sponsor approves money and time, not diagrams.
  6. Anticipate the three questions every reviewer asks: what happens when this fails, what does this cost at 10x volume, and what did we not build and why.
Foundations · 09

Good vs. bad architecture

Good architecture

  • Every requirement traces to a test and a runtime control
  • Decisions are written down before memory fades, with the losing options intact
  • NFRs carry numbers, not adjectives
  • Failure paths are designed before happy paths
  • Cost is a unit economic, not a lump sum
  • The package stays smaller than the sum of what it indexes

Bad architecture

  • Diagrams exist; nothing traces back to a requirement
  • Decisions live in someone's memory or a Slack thread
  • NFRs say "fast" and "scalable" with no number attached
  • The failure path is "we'll add retries later"
  • Cost is a single number nobody can decompose
  • The architecture document duplicates every other discipline's artifact in full

Foundations · 11

The review lens

The checklist an approver — a sponsor, a governance board, a fellow architect — should run before signing off on an architecture package:

#Check
1Does every requirement in the BRD trace to a design element, a build artifact, a test, a runtime control, and a governance rule?
2Does every significant decision have an ADR that shows the options it beat, not just the option chosen?
3Do the NFRs carry numbers a QA team could actually test against?
4Does the cost model express a real unit economic, and does the 12-month TCO reconcile with the roadmap's phasing?
5Does the roadmap have explicit approval gates, not just dates?
6Is there a named failure path, retry strategy, and recovery path for every external dependency?
7Does the security & governance view name the specific regulatory/compliance regime this system must satisfy?
8Could a competent engineer who was not in the room implement this from the package alone?

Capstone case study

ClaimSight AI — program overview

The carrier

Meridian Mutual Insurance — a regional property & casualty carrier operating in six Midwestern states, ~450,000 in-force policies (auto and homeowners), roughly 210,000 claims filed per year, $180M in annual claims volume. Claims are administered on Guidewire ClaimCenter; policies on a legacy policy administration system (PolicyStream). Claims intake today is phone- and paper-first.

The problem

Average claim cycle time is 14 days. Adjusters carry an average caseload of 145 open claims. First-notice-of-loss (FNOL) intake is manual and inconsistent, damage estimates vary adjuster to adjuster by as much as 30%, and fraud detection is entirely reactive — flagged after payout, not before.

The initiative

ClaimSight AI — an AI-assisted FNOL intake, computer-vision damage estimation, and fraud-signal triage system, fronted by a redesigned adjuster portal. A policyholder reports a loss through a conversational web/voice intake; uploaded photos are scored by a computer-vision damage-estimation model; an LLM summarizes the claim file for the assigned adjuster; a fraud-signal service scores the claim in near-real-time against telematics and historical patterns; low-risk, high-confidence claims are auto-triaged toward fast-track settlement, everything else routes to a human adjuster with an AI-drafted summary already attached.

1. Purpose & scope

This document is the single source of truth for the technical architecture of ClaimSight AI. 2. Business context & drivers

Meridian Mutual's claims cycle time (14 days average) and adjuster caseload (145 open claims/adjuster) are both above the regional carrier median, driving higher loss-adjustment expense and depressed policyholder satisfaction (NPS 31, versus a 45 regional benchmark). ClaimSight AI directly targets cycle time, cost per claim, and estimate consistency — see the KPI targets in the case study overview.

3. C4 context view

ClaimSight AI sits between the policyholder/adjuster actors and three systems of record it does not own: PolicyStream (policy administration), Guidewire ClaimCenter (claims management), and a third-party telematics & photo-estimation vendor. It reports summary claim volumes to the state Department of Insurance (DOI) on a scheduled batch cadence.

Inside the ClaimSight AI boundary, ten deployable containers separate intake, AI inference, fraud scoring, integration, and the adjuster-facing portal. ADR-001 — Damage estimation: build vs. buy vs. hybrid

Accepted

Context. Meridian needs computer-vision damage estimation accurate enough to auto-triage 60% of auto claims within a 6–8 week window ahead of the pilot gate, without giving up long-term control of a model this central to claims cost.

Build in-house

Full control, full IP — but 6–9 month build, high upfront cost, unproven accuracy at launch.

Rejected — too slow

Buy (vendor API)

Fast (2–4 weeks), cheap short-term — but opaque scoring, high lock-in, no tuning to Meridian's loss patterns.

Rejected — accuracy risk

Hybrid (chosen)

License a base CV model, fine-tune on Meridian's historical claim-photo/settlement pairs. 6–8 weeks, tunable, IP retained on the fine-tuning layer.

Selected

Decision. License a base computer-vision damage-estimation model and fine-tune it on Meridian's own historical claims data; do not build from scratch or take a vendor's model unmodified.

Consequences. Ongoing per-inference licensing cost (see Cost Model) and a dependency on the vendor's base-model roadmap. Accepted because it is the only option that hits both the pilot timeline and the accuracy bar the auto-triage KPI requires.

ADR-002 — LLM vendor for claims summarization

Accepted

Context. The AI Claims Summarization Service needs an LLM that can read a claim file (photos, notes, fraud signals) and draft an adjuster-facing summary that is accurate, non-fabricating, and safe to show inside a regulated workflow — with an enterprise contract Meridian's security team will sign off on.

Self-hosted OSS LLM

No per-token vendor cost, full data control — but requires standing up and maintaining GPU infra Meridian's DevOps team doesn't run today, and materially weaker instruction-following on long claim files.

Rejected — ops burden

Claude via Anthropic API (chosen)

Strong long-context accuracy on structured claim files, enterprise data-handling terms, no training on customer data by default.

Selected

GPT via Azure OpenAI

Comparable capability and enterprise terms — viable second choice, but Meridian's existing enterprise agreement and prior security review already cover Anthropic.

Rejected — no existing agreement

Decision. Use Claude via the Anthropic API for claims summarization, retrieval-grounded on the claim's own file only — never open-web generation.

Consequences. Per-token cost scales with claim volume (see Cost Model); accepted because summarization quality directly affects adjuster trust and the CSAT KPI. Summary is always advisory — see ADR-008 for the human-in-the-loop boundary.

ADR-003 — Integration pattern with Guidewire ClaimCenter

Accepted

Context. ClaimSight AI must create and update claims in Guidewire without becoming tightly coupled to its schema, and without either system silently drifting out of sync during peak (catastrophe) load.

Direct DB access

Fastest to build — but couples ClaimSight to Guidewire's internal schema, breaks on every Guidewire upgrade, no transactional isolation.

Rejected — fragile

Point-to-point REST

Simple for one integration — but doesn't scale as more systems need claim events, and retries have nowhere to queue under Guidewire downtime.

Rejected — doesn't scale

API-led via Integration Bus (chosen)

Guidewire Connector adapter behind an event bus; retries queue safely, other consumers (fraud, reporting) can subscribe without new point-to-point links.

Selected

Decision. All Guidewire writes go through a dedicated adapter service behind the Integration Bus, never direct database access, per CLAUDE.md's integration boundary rules.

Consequences. Adds one hop of latency (~150–300ms) versus direct access; accepted because it buys resilience during catastrophe-volume spikes and decouples ClaimSight's release cadence from Guidewire's.

ADR-004 — Claims data residency & storage

Accepted

Context. Meridian operates in six states with differing DOI data-handling expectations. The data platform needs one model the Data Engineering and Governance teams can both reason about.

Per-state silos

Cleanest regulatory isolation — but multiplies pipeline and model-training complexity by six, and cross-state fraud patterns become invisible.

Rejected — fragments AI training data

Unified lake, state-tagged (chosen)

Single data lake with a mandatory state column enforced at write time; row-level access policies handle state-specific rules.

Selected

Guidewire-only (no separate lake)

No new infrastructure — but Guidewire isn't built for CV training data or ML feature pipelines; would bottleneck AI Engineering entirely.

Rejected — wrong tool

Decision. One Claims Data Lake (Postgres + S3) with a mandatory state column and row-level policies, not per-state physical silos.

Consequences. Requires disciplined schema governance from Data Engineering to keep the state tag authoritative; accepted because it keeps the fraud model trainable across the full six-state pattern while still satisfying per-state DOI export requirements.

ADR-005 — Deployment topology

Accepted

Context. The pilot must ship within the Phase 3 window (see Delivery Roadmap); the eventual GA footprint spans six states with catastrophe-driven volume spikes.

Multi-region active-active

Best availability ceiling — but roughly doubles run cost and DevOps operational complexity before the pilot has even validated demand.

Rejected — premature for pilot

Single-region + warm DR (chosen)

Meets the 99.5% availability NFR and 4h RTO at pilot-appropriate cost; DR region is provisioned but not serving traffic.

Selected

Single-region, no DR

Lowest cost — but fails the RTO/RPO NFR outright and is unacceptable given claims-payment continuity obligations.

Rejected — fails NFR

Decision. Launch single-region with a warm-standby DR region; revisit multi-region active-active only if GA volume data shows it's warranted.

Consequences. DR failover is a manual-triggered runbook step, not automatic, for launch; accepted as the right cost/availability trade for a pilot-stage system, to be re-opened at the GA readiness gate.

ADR-006 — Fraud signal scoring architecture

Accepted

Context. Fraud scoring needs to influence adjuster routing before a claim is assigned, not after settlement, to have any preventive value.

Batch (nightly)

Simple to build — but scores arrive after claims are already assigned and, in some cases, already paid. Defeats the purpose.

Rejected — too late

Near-real-time streaming (chosen)

Fraud Signal Service scores each claim within the FNOL flow (step 4 in the sequence view), influencing triage before adjuster assignment.

Selected

Synchronous inline blocking

Guarantees freshness — but couples FNOL latency directly to fraud-model latency and risks blocking legitimate claims on a slow model call.

Rejected — latency coupling

Decision. Fraud scoring runs as a near-real-time streaming service, called in parallel with damage estimation (not blocking, not nightly-batch).

Consequences. Requires a streaming feature pipeline from Data Engineering; accepted because preventive fraud signal only has value before, not after, claim assignment.

ADR-007 — Adjuster Portal frontend framework

Accepted

Context. The Adjuster Portal and FNOL Intake App are new builds; Meridian's existing internal tools use a mix of frameworks with no single standard.

Angular

Strong enterprise conventions — but steeper ramp for the current engineering bench, which skews React-experienced.

Rejected — team fit

React (chosen)

Matches current engineering team experience; component reuse between Adjuster Portal and FNOL Intake App is straightforward.

Selected

Vue

Lightweight, fast to prototype — but smallest internal talent pool of the three, raises long-term maintainability risk.

Rejected — smallest talent pool

Decision. Build both the Adjuster Portal and FNOL Intake App in React.

Consequences. None material — this is a low-blast-radius, easily-reversible implementation decision, logged for completeness per the traceability discipline, not because it was contested.

ADR-008 — Model risk governance: human-in-the-loop threshold

Accepted

Context. AI-influenced claims triage sits inside a regulated workflow; Meridian's Governance function and state DOI examiners both need a defensible, auditable boundary between AI assistance and human accountability.

Full automation

Maximizes cycle-time reduction — but removes human accountability from a regulated financial decision. Unacceptable governance exposure.

Rejected — governance boundary

Threshold-gated human review (chosen)

Claims scoring above the confidence/risk threshold auto-triage; everything below requires adjuster sign-off before settlement.

Selected

Manual review of all claims

Safest posture — but forfeits the entire cycle-time and cost-per-claim business case for the initiative.

Rejected — defeats the ROI case

Decision. Claims below the damage-estimate confidence threshold (0.80) or with an elevated fraud-signal flag always route to a human adjuster; auto-triage never bypasses this gate.

Consequences. Caps the achievable auto-triage rate at the model's real confidence distribution (target 60%, not 100%); accepted as a hard governance boundary, not a tunable business lever — see GOV-CLAIMSIGHT-CompliancePolicy-v1.1.
