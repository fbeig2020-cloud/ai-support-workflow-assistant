Integration Engineer Field Guide

The 20% of integration engineering an AI Solution Architect needs to direct, evaluate, and approve AI-generated integrations between separate systems — not to hand-code every adapter.

Who this is for
You are becoming an AI Solution Architect in the Colaberry Enterprise AI Leadership Accelerator. You will rarely write the integration code yourself. You will review a pull request, an OpenAPI spec, or an AI agent's proposed wiring between a portal, a legacy system, and two AI services — and you must know, in under five minutes, whether it is safe to approve. This guide teaches that judgment, illustrated against one concrete initiative.

How to use this guide

Read the example initiative first — every concept and every document below refers back to it. Then either read top to bottom, or jump straight to what you need using the search box in the header or the Ask the guide panel on the right, which answers questions from this guide's own content, fully offline, with no external calls.

What you must be able to do
Read an integration architecture diagram and spot the seam that will break first. Read an API contract and know if versioning and auth are sound. Read a sequence diagram and ask “what happens on the failure branch?” Read a retry policy and know if it can create duplicate money movement. Read a data mapping table and spot an unsourced field.
What you are not doing
You are not writing the SDK client for the fraud-scoring vendor. You are not hand-tuning the OAuth token-refresh loop. An AI coding agent (or a specialist integration engineer) builds that. Your job is to have set the contract, the failure requirements, and the review bar before it ships — and to catch it if those requirements are missing.

The example initiative

Every deliverable in this guide is written for one invented initiative: ACTA — the Aegis Auto Claims Triage Assistant, at a mid-size auto insurer, Aegis Mutual. This is the same running example used across the QA and UX Design field guides in this curriculum track; here it is viewed through the integration layer that connects its systems.

A claimant reports a car accident (a First Notice of Loss, or FNOL). ACTA's job is to gather everything a human adjuster would need, score it for severity and fraud risk, and either fast-track it for automatic reserve approval or route it to a human — never approving a payout without the review gates this guide documents.

Why integration exists

No system of value lives alone. ACTA is not one application — it is the seams between six applications, three of which Aegis Mutual does not own. Integration engineering is the discipline of making those seams predictable when every system on the other side of them is not: it can be slow, it can be down, it can change its contract, and it can send you the same message twice.

The governing question
Every integration decision answers one question: when the system on the other end misbehaves, what happens here? A design that only answers “what happens when it works” is not a design — it is a demo. This is the same doctrine as this program's Failure-First Design principle, applied specifically to the wire between two systems.

For ACTA, “the other end” is sometimes a 20-year-old legacy system that was never built for this call volume (PAS), and sometimes a vendor AI service you do not control and cannot patch (DocScan, SentinelScore). Both require the same discipline: assume failure, design for it, and prove it in a test.

REST vs GraphQL vs event APIs

Three shapes cover almost every integration you will review. The choice is not aesthetic — it follows from who owns the data, how many clients query it, and whether the receiver needs to act now or eventually.

StyleBest forTrade-offUsed in ACTA for

GraphQLMany heterogeneous clients (web, mobile, partner) each needing a different slice of a large graphQuery complexity/cost control, caching is harder, a single query can accidentally fan out to N backend callsNot used here — ACTA has one internal consumer per contract, so REST's simplicity wins. Reviewer's rule of thumb
If an AI agent proposes GraphQL for a single-consumer, single-purpose service call, ask why. GraphQL earns its complexity when query shape varies by client; ACTA's server-to-server calls do not have that problem, and REST's simpler contract, caching, and tooling win.

API contracts & versioning

A contract is a promise about shape: request fields, response fields, status codes, and error format. Once a consumer depends on it, changing it without warning breaks them — even if your side still “works.”

Change typeExampleSafe to ship silently?
Additive, optionalNew optional response field claim.adjusterNotesYes — consumers ignoring unknown fields are unaffected
Additive, requiredNew required request fieldNo — breaks every existing caller; needs a major version
Field removed or renamedpolicy_no → policyNumberNo — breaking; requires deprecation window
Type or enum narrowedStatus enum drops a value a consumer still checks forNo — breaking
Error code semantics change404 changes meaning from “not found” to “soft-deleted”No — breaking even though the HTTP status is unchanged

ACTA versions its own API by URI (/v1/). See Deliverable 2 for the full policy. The rule a reviewer applies is simple: a breaking change needs a new major version and a coordinated migration, not a same-version patch.

Authentication: keys, OAuth, tokens

Every seam needs to answer “who is calling, and are they allowed to do this?” ACTA uses three different mechanisms because its three kinds of caller have three different trust profiles.

MechanismUsed whereWhy this one
OAuth 2.0 client-credentialsPortal BFF → ACTA; ACTA → SentinelScore; ACTA → ClaimPayService-to-service, no human present, short-lived scoped tokens that expire and rotate automatically
Mutual TLS + static service tokenACTA → PASLegacy constraint — PAS predates OAuth support; mTLS adds a network-layer identity guarantee OAuth alone would not, and the token is rotated quarterly by a runbook
HMAC-signed webhookInbound: DocScan & ClaimPay callbacksThe caller is a third party initiating contact to Aegis; a shared-secret signature proves the payload came from the real vendor and was not tampered with in transit or replayed
What a reviewer must never accept
An API key or bearer token in a URL query string (it ends up in logs and browser history). A webhook receiver that trusts the payload without verifying a signature. A service token that never rotates. A scope broader than the caller needs (e.g. a portal token that can also read other claimants' claims).

Webhooks vs polling

When ACTA needs to know “is the OCR job done yet?” it has two options, and it actually uses both — one as the primary path, one as the safety net.

Webhook (push) — primary
DocScan calls POST /webhooks/docscan/ocr-complete on ACTA the moment the job finishes. Low latency, low load on both sides. Requires ACTA to expose a public, authenticated endpoint and to handle the message arriving zero, one, or more than once — webhooks are typically at-least-once delivery, never exactly-once.
Polling (pull) — fallback
If no webhook has arrived within 90 seconds, ACTA calls GET /v1/ocr-jobs/{id} itself. Higher latency and load, but it needs no inbound network exposure from the vendor's side and survives a lost or undelivered webhook. It is the fallback precisely because the webhook can fail silently and polling cannot.
Reviewer's check
Any design that uses webhooks only, with no poll-based reconciliation and no signature verification, is incomplete. Ask: what happens if the webhook is never delivered? What happens if it is delivered twice? Both must have a documented answer — see Deliverable 3 for the worked duplicate-delivery case.

Synchronous vs asynchronous

Synchronous: the caller blocks and waits for the response. Asynchronous: the caller moves on and is notified (or checks back) later. The choice is driven by whether the caller's next step actually depends on the result.

SeamModeWhy
Portal → ACTA intakeSyncThe claimant is waiting on screen for a confirmation number
ACTA → SentinelScore fraud checkSyncThe routing decision cannot be made until the fraud score is known; a 3s timeout keeps this from stalling the claim
ACTA → DocScan OCRAsyncDocument extraction can take 30–90s; nothing else in the flow is blocked on it, so ACTA starts the job and continues
ACTA → NotifyHubAsyncA claim must never fail or slow down because an SMS provider is having a bad day
Common mistake
Making a call synchronous “just to keep it simple” when the caller does not actually need the result immediately. This is how a slow, non-critical notification service ends up able to stall a money-moving claims pipeline. If the answer to “does my very next step require this result?” is no, it should not block.

Idempotency, retries & backoff

Idempotent: running the same operation twice (with the same key) produces one effect, not two. This is non-negotiable on any call that moves money, creates a record, or sends a communication — because retries, at-least-once webhook delivery, and network blips will cause duplicates to be attempted.

ACTA's idempotency key
Every write to ClaimPay carries an Idempotency-Key header shaped {claimId}:{operationType}, e.g. CLM-88213:reserve-hold. ClaimPay stores the key with a hash of the request body; a retry with the same key and same body returns the original cached response instead of creating a second hold. A retry with the same key but a different body is rejected with 409 Conflict — that mismatch usually means a bug, not a legitimate retry.

Retries themselves must be capped and spaced, not immediate and infinite: exponential backoff with jitter (e.g. 500ms, 1s, 2s, capped at 4 attempts) avoids hammering a struggling upstream and avoids every failed client retrying in lockstep (the “thundering herd”). See the backoff curve in Deliverable 4.

Timeouts & circuit breakers

A call with no timeout is a call that can hang forever, holding a thread, a connection, and the claimant's patience hostage. Every outbound call in ACTA has an explicit budget, sized to what the downstream can realistically deliver:

CallTimeoutWhy this number
ACTA → SentinelScore3sGates the routing decision; must fail fast to a safe default rather than stall the claim
ACTA → PAS8sLegacy system, historically slow under load; generous but bounded
ACTA → ClaimPay6sMoney-moving; balances vendor SLA against not leaving a reserve in limbo

A circuit breaker goes one step further than a timeout: after N failures in a window, it stops calling the failing service entirely for a cool-down period, failing fast instead of piling up more timeouts on an already-struggling upstream. ACTA opens PAS's circuit after 5 failures in 60 seconds. See the full state diagram in Deliverable 4.

Fallback still has to be safe
When SentinelScore's circuit is open, ACTA does not skip the fraud check — it fails closed, routing every claim to a human adjuster until the circuit recovers. A degraded path that silently skips a safety gate is worse than an outage.

Data mapping & transformation

Six systems, six different ideas of what a “claim” looks like. PAS encodes policy status as a single legacy character. The portal sends loss date as a US-format string. SentinelScore returns fraud signals as vendor-specific codes. Someone has to reconcile all of it into one canonical Claim object — and that reconciliation has to be traceable, not invented.

The rule a reviewer enforces
Every field on the target (canonical) object must cite a real source field and a stated transformation. “Unsourced field” — a target field with no documented origin — is the data-mapping equivalent of an orphan test: it means someone typed a value in without a traceable source, and it will be wrong the moment the assumption behind it changes.

Normalization matters as much as sourcing: currency is stored as integer cents (never float dollars), dates as ISO-8601 UTC, states as USPS 2-letter codes, and every enum has a fixed, documented value set. See the full field-by-field table in Deliverable 5.

Rate limits

A rate limit is the other side's way of saying “this much, no faster.” Ignoring it does not make your integration faster — it makes it get throttled, then blocked, then possibly suspended by the vendor.

SeamLimitConstraint source
Portal BFF → ACTA100 req/min per clientACTA's own protection against a runaway portal bug
ACTA → PAS20 req/sLegacy system's documented ceiling — exceeding it degrades PAS for every other consumer at Aegis, not just ACTA
ACTA → SentinelScore50 req/s (contract tier)Vendor SLA; above this, requests return 429
Reviewer's check
A 429 response must be honored via its Retry-After header, not treated as a generic retryable error on a fixed backoff schedule — the server is telling you exactly how long to wait. See the error code table in Deliverable 2.

Error handling & dead-letter queues

Not every failure is retryable, and not every retryable failure eventually succeeds. Both cases need an explicit destination, not a silent drop.

SituationHandling
Client error (400, 401, 403, 404, 422)Not retried — the request itself is wrong; fix and resubmit
Transient server error (429, 502, 503, 504)Retried with capped exponential backoff
Retries exhausted on a non-critical async callMessage routed to a dead-letter queue (DLQ) with full context; does not block the claim (e.g. NotifyHub)
Retries exhausted on a critical sync callCircuit opens; claim routed to a manual queue with a DLQ entry for audit (e.g. ClaimPay)
Forbidden pattern
catch (e) {} — a silently swallowed failure. Every caught exception in ACTA is tagged with a stable error_class (e.g. UpstreamUnavailable, ValidationError) and logged with a correlation ID before any fallback runs. A generic Error in a production log means the catch block needs to be more specific. Full DLQ design in Deliverable 4.

The architect's review lens

When an AI agent (or a specialist engineer) hands you an integration to approve, run this checklist. It is the fast version of everything above.

#CheckFails if…
1Every external call has an explicit timeoutA call relies on a framework default no one chose
2Every write is idempotentRe-running the operation with the same key could create a duplicate
3Retries are capped, backed off, and scoped to retryable errors onlyA 400 or 404 gets retried; or there is no retry limit
4A circuit breaker (or equivalent) exists on critical sync callsRepeated failures keep hammering a struggling upstream indefinitely
5Webhooks verify signature, reject replays, and dedupe deliveriesAny inbound POST is trusted and processed unconditionally
6Sequence diagrams show the retry path and the failure branchOnly the happy path is documented
7Every data-mapping target field has a cited source and normalized typeA field appears with no documented origin
8Contract changes are versioned; breaking changes get a new major versionA required field is added, or a field is removed, in place
9Failures are classified, logged with a correlation ID, and never silently swallowedA bare catch {} appears anywhere in the path
10A fail-closed fallback exists for any safety-gating callA fraud check or approval gate is skipped when its dependency is down
The one-sentence version
If you can't point to the timeout, the idempotency key, the retry cap, and the failure branch for a given call, it is not ready to approve — regardless of how clean the happy path looks.

1. Purpose & scope

This document is the architectural source of truth for how ACTA connects the Claimant Portal, Policy Admin System (PAS), DocScan AI, SentinelScore, ClaimPay, and NotifyHub. It defines every seam's protocol, delivery mode, and non-functional budget. Endpoint-level request/response schemas live in Deliverable 2; call ordering and failure branches live in Deliverable 3.

2. Integration pattern: orchestration over choreography

ACTA Orchestrator is a hub-and-spoke integration: it is the single component that calls PAS, DocScan, SentinelScore, ClaimPay, and NotifyHub, and no two spoke systems call each other directly. The alternative — choreography, where each system reacts to events from any other — was rejected for this initiative because the routing decision (fast-track vs. adjuster vs. SIU) requires a single component to hold the full picture before acting, and because a regulated, money-moving flow needs one auditable place where the decision logic lives, not logic scattered across six event handlers.

When choreography would win instead
If ACTA had a dozen loosely-coupled downstream consumers reacting independently to “claim created” with no shared decision to make, an event-choreography model would reduce coupling better than a hub. The right answer follows from whether a decision needs a single owner — here, it does.

5. Non-functional requirements

  • End-to-end latency: p95 ≤ 12s from intake submission to routing decision (excludes async OCR, which is not on the routing-decision critical path unless the claim requires document evidence to route).
  • Availability: ACTA Orchestrator itself targets 99.9%; it must degrade gracefully (fail closed to human review) rather than go fully unavailable when any single downstream is impaired.
  • Data residency & PII: all cross-system payloads carrying policyholder PII are redacted in logs; DocScan and SentinelScore contracts prohibit vendor retention of raw images/PII beyond the processing window (contractual, verified annually).
  • Auditability: every claim's full call graph is reconstructable from its correlation ID across all six systems' logs for a minimum of 7 years (regulatory retention).

4. Dead-letter handling

A message routes to the DLQ when its retries are exhausted and the operation is not one where blocking the caller is acceptable (async paths), or when a critical sync path's circuit opens and the claim needs a manual-review audit trail.

DLQ redrive runbook (summary)
1. Alert fires at DLQ depth ≥ 25 or any single entry older than 4 hours. 2. On-call inspects the entry's error_class and correlation ID to confirm the upstream has recovered. 3. Redrive replays the original request through the idempotent endpoint — safe by construction, because the same idempotency key either creates the effect once or returns the cached result. 4. Entries that fail redrive twice escalate to the claims-engineering on-call per the Escalation Protocol.

FAQ

Why REST instead of GraphQL for ACTA's internal calls?
Every server-to-server seam in ACTA has exactly one consumer with a fixed, known shape. GraphQL earns its complexity when many heterogeneous clients need different slices of a large graph; that isn't ACTA's problem, so REST's simpler contract and caching win. See REST vs GraphQL vs event APIs.
What's the difference between a timeout and a circuit breaker?
A timeout bounds one call. A circuit breaker looks at the pattern across many calls and, after enough failures, stops attempting new calls for a cool-down period so a struggling downstream isn't hammered further. See Timeouts & circuit breakers.
How does ACTA guarantee a reserve hold is never created twice?
Every reserve request carries an Idempotency-Key shaped {claimId}:reserve-hold. ClaimPay stores the key with the request hash; a retry with the same key and body returns the cached response instead of creating a second hold. See Deliverable 4.
What happens if the DocScan webhook never arrives?
ACTA polls GET /v1/ocr-jobs/{id} if no webhook lands within 90 seconds. After 3 poll misses, the document routes to manual review rather than stalling the claim indefinitely. See Webhooks vs polling.
Why does ACTA fail closed, not open, when the fraud service is down?
Because the fraud check is a safety gate, not an optimization. Failing open (skipping the check) would let claims auto-approve with zero fraud screening during every SentinelScore outage. Failing closed routes everything to a human until the gate is back. See Timeouts & circuit breakers.
What counts as a breaking API change?
A removed or renamed field, a new required field, a narrowed enum, or a change in what an existing error code means. Anything that could make an existing, unmodified consumer start failing. See API contracts & versioning.
Why is currency stored as integer cents, not a float?
Floating-point arithmetic cannot represent most decimal currency values exactly, and repeated arithmetic compounds the error — unacceptable on a field that determines a payout. Integer cents avoids the entire class of bug. See Deliverable 5.
What goes to the dead-letter queue, and how does it get resolved?
Messages whose retries are exhausted on a non-blocking async path, or a critical sync call whose circuit has opened. An on-call runbook inspects, confirms the upstream has recovered, and redrives the message through the same idempotent endpoint. See Deliverable 4.
How is a webhook prevented from being replayed?
Every inbound webhook carries an HMAC-SHA256 signature and a timestamp; ACTA rejects any payload whose timestamp is more than 5 minutes old, even if the signature itself is valid. See Authentication: keys, OAuth, tokens.
Why hub-and-spoke instead of event choreography?
The routing decision needs one component holding the full picture (severity, fraud score, reserve estimate) before it acts, and a regulated, money-moving flow needs one auditable place where that decision logic lives. See Deliverable 1, section 2.

Glossary

TermDefinition
RESTAn architectural style for resource-oriented APIs over HTTP, using verbs (GET/POST/PUT) and status codes as the contract.
GraphQLA query language letting clients request exactly the shape of data they need from a single graph endpoint.
WebhookAn inbound HTTP callback a third party sends to notify you of an event, instead of you asking them.
PollingRepeatedly asking “is it done yet?” on a schedule, instead of waiting to be told.
Idempotency keyA caller-supplied identifier ensuring a retried operation has one effect, not many.
Circuit breakerA guard that stops calling a repeatedly-failing dependency for a cool-down period, failing fast instead of piling up timeouts.
Dead-letter queue (DLQ)A holding area for messages that exhausted retries, preserved with context for manual triage instead of being dropped.
OAuth 2.0 client-credentialsA service-to-service auth flow where a client exchanges an ID/secret for a short-lived, scoped bearer token — no human or browser involved.
HMACA keyed hash used to sign a payload so the receiver can verify it came from a holder of the shared secret and was not altered.
mTLSMutual TLS — both client and server present certificates, proving identity in both directions at the network layer.
Exponential backoffDoubling (or similarly scaling) the delay between retry attempts, so repeated failures don't hammer a struggling system at a constant rate.
JitterRandomizing backoff delay slightly so many clients retrying the same failure don't all retry in the same instant.
Rate limitA cap on how many requests a consumer may make in a time window, enforced by the provider.
SLAService Level Agreement — a contracted commitment on availability, latency, or another measurable dimension.
Correlation IDA single identifier propagated through every call and log line for one logical operation, enabling end-to-end tracing.
Contract versioningThe discipline of marking breaking API changes with a new version and giving consumers a migration window.
Fail-closed / fail-openFail-closed denies/escalates by default when a dependency is unavailable (safer for gates); fail-open allows by default (safer for availability, riskier for controls).
At-least-once deliveryA messaging guarantee that a message will be delivered one or more times — never zero, but duplicates are possible and must be handled by the receiver.
Orchestration vs. choreographyOrchestration: one component directs every call. Choreography: components react independently to events with no central director.
Synchronous / asynchronousSync: the caller blocks for the result. Async: the caller proceeds and is notified, or checks back, later.
Timeout budgetThe maximum time an outbound call is allowed to take before it is aborted, sized to the downstream's realistic latency.
