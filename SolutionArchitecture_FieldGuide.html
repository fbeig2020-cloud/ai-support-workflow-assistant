Why Solution Architecture Exists

Left alone, an AI coding agent (or a fast-moving engineering team) optimizes for the request in front of it: make this endpoint work, make this feature ship. Solution architecture exists to hold the system-level concerns that no single feature request will ever surface on its own — will this still work at 10x load, can two teams ship to it without blocking each other, what happens when a dependency is down at 2 a.m., and can a new engineer explain it in a sitting. A solution architect's job is not to write more code than anyone else; it is to make the handful of decisions that are expensive to reverse, and to make them before they get baked into hundreds of files.

In an AI-assisted delivery model, this role becomes more important, not less. An AI agent will happily generate a technically-working monolith, a technically-working microservice mesh, or a technically-working event-driven system for the same requirements — it has no opinion on which one your team can actually operate. The architect supplies the judgment: which trade-offs matter for this system, at this scale, with this team. That judgment is what you are here to build.

The 20%, Part 1: Quality Attributes (Non-Functional Requirements)

Functional requirements describe what the system does. Quality attributes describe how well it keeps doing it — and they are the requirements most likely to be silently dropped by an AI-generated design unless someone with your role insists on them being explicit and measurable.

AttributeThe question it answersTypical measure
AvailabilityHow much downtime can the business tolerate?% uptime (e.g. 99.9%), error budget
Latency / PerformanceHow fast must a response be, under load?P50 / P95 / P99 response time
ThroughputHow much volume must the system absorb at peak?Requests/sec, events/sec
ScalabilityHow does the system grow with load — and how fast?Horizontal scale-out time, cost curve
DurabilityCan data survive a failure without loss?Replication factor, backup RPO
SecurityWho can do what, and how is that enforced?AuthN/AuthZ model, encryption standard
ObservabilityCan you tell what the system is doing right now?Logging/tracing coverage %
MaintainabilityHow fast and safely can it change?Deployment lead time, test coverage
Cost / EfficiencyWhat does it cost to run at scale?$ per transaction, infra cost ratio
Disaster RecoveryHow fast can service resume after a major failure?RTO (time to restore), RPO (data loss window)
The rule that matters mostEvery quality attribute must have a measurable target, not an adjective. "Highly available" is not a requirement. "99.9% monthly uptime, measured by synthetic probe every 60s" is. If an AI-generated NFR spec uses words like "fast," "robust," or "scalable" without a number attached, send it back — see Document 4 for what a complete version looks like.

The 20%, Part 2: Architecture Styles

Three styles cover the large majority of real decisions you will evaluate. None is universally "better" — each is a different way of trading coupling for coordination cost.

StyleCouplingDeploymentFailure blast radiusBest forWatch-outs
MonolithHigh (shared process, shared DB)Single unit, all-or-nothingOne bug can take down everythingSmall teams, early-stage products, low operational maturityBecomes a bottleneck as team & codebase grow; slow deploys
Service-Oriented / MicroservicesMedium — services own their data, coordinate via APIsIndependent per serviceContained to the failing service (if isolated well)Multiple teams, independently-scaling domains, differing tech needsDistributed-systems tax: network calls, data consistency, more infra to operate
Event-DrivenLow — producers and consumers don't know about each otherIndependent, asynchronousIsolated; backpressure instead of cascading failureHigh-volume streams, real-time reactions, decoupled domainsHarder to trace a single request end-to-end; eventual consistency must be designed for, not assumed

These are not mutually exclusive — most real systems, including the one in this guide, are event-driven microservices: independently deployable services that communicate primarily through an event bus, with synchronous REST reserved for request/response paths a user is actively waiting on. See ADR-001 for how this choice was justified against Meridian's actual load, not against a trend.

The 20%, Part 3: The C4 Model

The C4 model gives you four zoom levels for describing a system, so a design can be reviewed by the right audience at the right altitude instead of one overloaded diagram trying to serve everyone.

LevelShowsAudience
1. ContextThe system as one box, its users, and the external systems it talks toExecutives, product, anyone needing the 30-second picture
2. ContainerThe deployable units inside the system (services, apps, data stores, queues) and how they connectArchitects, tech leads, ops
3. ComponentThe internal building blocks of one container and their responsibilitiesEngineers building or reviewing that container
4. CodeClasses / modules — usually left to IDE-generated diagrams, rarely hand-drawnEngineers actively coding

Document 2 in this guide provides Levels 1–3 for SKU Sentinel. As a reviewer, your job is to confirm each level is internally consistent with the others — every box named in the Container diagram should trace back to a line in the Context diagram's system boundary, and every arrow should have a direction and a purpose, not just a line.

The 20%, Part 4: Architecture Decision Records (ADRs)

An ADR captures one significant, hard-to-reverse decision: what was decided, what else was considered, why it lost, and what it costs us going forward. ADRs are the single highest-leverage artifact for an AI-assisted architecture process, because they force the "why," not just the "what" — which is exactly the part an AI agent will skip unless explicitly asked for it.

FieldPurpose
StatusProposed / Accepted / Superseded / Deprecated — decisions have a lifecycle
ContextThe forces at play: load, team, constraints, deadline pressure
DecisionThe one sentence that states what was chosen
Rejected OptionsWhat else was seriously considered, and specifically why it lost
ConsequencesWhat this decision makes easier, and what it makes harder — every decision has both
Reviewer red flagAn ADR with no rejected options is not a decision record — it's a decision announcement. If the AI-generated ADR only describes the winning option, ask it to regenerate with at least two genuine alternatives and their honest trade-offs. Document 3 gives you six worked examples.

The 20%, Part 5: Trade-off Analysis

Most technology choices are not "correct vs. incorrect" — they're a weighted balance across criteria that matter differently to different systems. A simple, defensible method:

  1. Pick criteria that matter for this system (not a generic checklist) — e.g. cost, operational burden, latency, team familiarity, vendor lock-in.
  2. Weight each criterion so the weights sum to 1.0, reflecting what actually matters for this decision.
  3. Score each option 0–10 per criterion, honestly — including the option your team is emotionally attached to.
  4. Multiply and sum to get a weighted total per option.
  5. Sanity-check the winner against the numbers you didn't put in the model — a spreadsheet does not know about your team's on-call fatigue.

Document 5 applies this method to two real SKU Sentinel decisions: the event bus platform, and build-vs-buy for demand forecasting.

The 20%, Part 7: Fitness Functions

A fitness function is an automated, repeatable test that checks whether the architecture still holds its intended shape — not whether the code compiles, but whether it still looks like the architecture you approved. Examples: a dependency-direction check that fails the build if a "core" module imports from an "adapter" module; a latency budget test that fails CI if P95 exceeds target under synthetic load; a coupling metric that flags a module importing from more than N others. Fitness functions turn "please don't do that" into something CI enforces automatically — the deterministic-execution principle applied to architecture itself.

The 20%, Part 8: Build vs. Buy

Lean Build when…Lean Buy when…
The capability is close to your core differentiatorIt's undifferentiated — the business doesn't win by having a better version of it
You need deep control over behavior or dataA mature vendor already solves it at a quality you can't beat cost-effectively
Your team has (or can build) the specific expertiseThe expertise required is scarce and expensive to hire for a one-time need
Long-term total cost of ownership favors owning itTime-to-market matters more than long-term unit economics right now

See ADR-004 for how this framework was applied to the demand-forecasting model itself — a case where the answer was neither a clean "build" nor a clean "buy," but a documented hybrid.

The Architect's Review Lens

When an AI agent hands you a design, this is the checklist that turns you from a passive recipient into the accountable approver:

  1. Does every quality attribute have a number, not an adjective?
  2. Is the architecture style justified against this system's actual load and team, or is it just the trendy default?
  3. Does every significant decision have an ADR with genuine rejected alternatives?
  4. Are the C4 diagrams internally consistent — does every container trace back to the context diagram?
  5. Does the design state what happens when each external dependency fails?
  6. Is there an idempotency story for every side-effecting operation (see this repo's non-negotiable rule on this)?
  7. Are trade-offs stated with real costs, not just the winning option's benefits?
  8. Is the complexity proportional to the load — no microservice sprawl for a low-volume system, no fragile monolith for a high-volume one?
  9. Is there a named owner and a review cadence for this architecture going forward?
  10. Could a competent engineer who wasn't in the room rebuild this system's intent from the documents alone?
This is the discipline in one sentenceYou are not being asked to out-engineer the AI. You are being asked to know which ten questions to ask it — and to recognize a bad answer when you hear one.

1. Executive Summary

SKU Sentinel is a real-time inventory intelligence and demand-forecasting platform for Meridian Retail Group's 240-store network. It replaces a nightly-batch, spreadsheet-assisted replenishment process with an event-driven system that ingests point-of-sale, ERP, warehouse, and e-commerce activity as it happens, maintains a continuously updated view of on-hand inventory per SKU per store, and runs short-horizon demand forecasts that drive automated stockout and overstock alerts to store managers and category analysts. The platform is expected to reduce stockout-driven lost sales by 30% and overstock markdown cost by 20% within twelve months of full rollout, against a $42M and $27M annual baseline respectively.

2. Business Context & Problem Statement

Meridian's current replenishment workflow reconciles POS sell-through against ERP stock levels once nightly, with store managers manually reviewing exception reports each morning. By the time a stockout risk is visible, it is frequently already a stockout — Meridian's own analysis attributes roughly 60% of stockout incidents to detection lag rather than to genuine unpredictable demand. The reverse problem, overstock, is driven by conservative manual reorder padding that is never revisited as sell-through patterns shift. Business requirements for SKU Sentinel are treated as approved inputs to this document; this SAD addresses how the system is built, not whether it should be.

9. Security Architecture

Authentication is OIDC/OAuth2 via Meridian's existing Azure AD tenant; the Store Manager Web App and API Gateway both validate JWTs and enforce role-based access (store-scoped for Store Managers, region/category-scoped for Analysts). Service-to-service calls inside the platform boundary use mTLS. Data at rest is encrypted (Azure-managed keys); data in transit is TLS 1.2+ throughout. SKU Sentinel does not process, store, or transmit cardholder data — POS integration carries SKU/quantity/timestamp only, not payment instrument data — and is therefore out of PCI-DSS scope. All secrets (SAP service account, Azure ML keys) are held in Azure Key Vault; no secret is ever logged, consistent with the repository's secrets-management rules.

11. Constraints & Assumptions

  • Requirements for SKU Sentinel are approved inputs; this document does not revisit business justification.
  • Meridian's Azure Enterprise Agreement is the assumed cloud platform; no multi-cloud requirement exists.
  • ~15% of stores operate on constrained/unreliable connectivity ("Tier 3" per Store entity's connectivity_tier) and require store-local buffering with replay-on-reconnect.
  • SAP ERP is treated as the system of record for SKU master data; SKU Sentinel does not duplicate ownership of that data.
  • Forecasting model retraining cadence (weekly) is an initial assumption, to be tuned once production drift metrics are available.

Each record below follows the same structure deliberately: Context, Decision, Rejected Options (with the specific reason each lost), and Consequences (including what the winning option costs us). An ADR without a rejected option is not a decision record — see Foundations, Part 4.

ADR-001 — Event-Driven Microservices over a Modular Monolith

Status: Accepted

Context. SKU Sentinel must ingest a high-volume, bursty stream from 240 stores (POS, ERP, WMS, e-commerce), keep a near-real-time inventory position, and run a compute-intensive forecasting workload — three workloads with very different scaling and change-cadence profiles. Roughly 15% of stores run on constrained connectivity and need to buffer-and-replay rather than block on a live call.

Decision. Build SKU Sentinel as event-driven microservices, with an event bus as the primary integration mechanism and REST reserved for synchronous, user-initiated request/response paths (dashboard reads, manual overrides).

Rejected Options.

OptionWhy it lost
Modular monolithCannot scale the forecasting workload (GPU/CPU-bound, bursty) independently of the transactional inventory-write path; one deploy pipeline forces every change through the same release cadence and blast radius
Synchronous microservices onlyWould require every service to be reachable in real time; incompatible with known store-network connectivity gaps and would create cascading timeouts under POS burst load (Black Friday)

Consequences. Gains: independent scaling per workload, tolerance for store connectivity gaps via replay, natural audit trail of domain events. Costs: eventual consistency on the read path must be designed for (not assumed away), and the team takes on operational responsibility for a distributed event backbone it has less experience running than a single database.

ADR-002 — Azure Event Hubs as the Event Backbone

Status: Accepted

Context. ADR-001 requires a durable, replayable, high-throughput event bus. Candidates evaluated: self-managed Apache Kafka, Confluent Cloud, AWS Kinesis, and Azure Event Hubs (Kafka-protocol compatible). Full scoring is in Document 5.

Decision. Use Azure Event Hubs in Kafka-compatible mode.

Rejected Options.

OptionWhy it lost
Self-managed KafkaLowest weighted score — highest operational burden for a team with no existing Kafka SRE bench, and no cost advantage once cluster operations staffing is priced in
AWS KinesisWould require a second cloud provider relationship for a single component; Meridian's Enterprise Agreement and existing identity/networking are entirely Azure
Confluent CloudClose second place; more Kafka-native tooling, but materially higher run-rate cost than a native Azure service for the same throughput, and one more vendor relationship to manage

Consequences. Gains: managed durability/replay, native Azure IAM integration, Kafka-protocol compatibility keeps consumer code portable if we outgrow it. Costs: a soft dependency on Azure-specific quota and throughput-unit tuning; some Kafka ecosystem tooling (e.g. certain Kafka Connect connectors) is not directly usable and needs an Azure-native equivalent.

ADR-003 — CQRS with a Denormalized Read Model for Inventory Queries

Status: Accepted

Context. The inventory write path (POS/ERP/WMS events changing on-hand quantity) and the read path (dashboards, alert evaluation, store manager app polling) have opposite shapes: writes are narrow and consistency-sensitive; reads are wide, high-volume, and latency-sensitive (P95 target <250ms — see NFR Spec).

Decision. Split into a command model (PostgreSQL, strongly consistent, owns validation) and a query model (Cosmos DB, denormalized per store/SKU, updated asynchronously from the same domain events).

Rejected Options.

OptionWhy it lost
Single shared relational model for both reads and writesRead-heavy dashboard queries at 240-store scale would contend with write-path transactions and force read replicas anyway — CQRS makes that split explicit rather than accidental
Full event sourcing (rebuild all state from event log)Rejected as over-engineering for this release: no current requirement for point-in-time state replay beyond the 7-day event retention window already provided by the event bus

Consequences. Gains: read and write paths scale independently; query latency is decoupled from write-path load. Costs: the read model is eventually consistent — a store manager can, for a small window (target <5s), see a stale on-hand quantity after a sale; the UI must communicate "as of" freshness rather than imply real-time truth.

ADR-004 — Hybrid Build/Buy for the Demand Forecasting Model

Status: Accepted

Context. Demand forecasting is close to SKU Sentinel's core differentiator, but general-purpose forecasting is a mature, well-solved problem with credible SaaS vendors (Blue Yonder, o9). Full scoring in Document 5.

Decision. Build the forecasting service and feature pipeline in-house on Azure ML (AutoML + custom Meridian-specific features: local events, weather, historical markdown cadence), rather than adopting a third-party forecasting SaaS wholesale.

Rejected Options.

OptionWhy it lost
Buy — full third-party forecasting SaaS (Blue Yonder / o9)Strong general accuracy, but weak on Meridian-specific signals (hyper-local promotions, store-level substitution behavior) that materially affect this use case, and would durably lock forecasting logic and its economics outside Meridian's control
Build fully from scratch (custom models, no managed ML platform)Would duplicate MLOps capability (experiment tracking, endpoint hosting, drift monitoring) Azure ML already provides; slower time-to-first-forecast with no offsetting long-term advantage

Consequences. Gains: forecasting logic and its data stay a Meridian-owned asset; team builds durable ML operations capability. Costs: Meridian owns model quality and drift monitoring long-term (see Risk R7); slower initial time-to-value than a SaaS "turn it on" path — mitigated by scoping v1 to a narrower SKU set (top 60% of volume) before full rollout.

ADR-005 — API Gateway with a Single Web BFF, No Separate Mobile BFF (Yet)

Status: Accepted

Context. Store managers access SKU Sentinel exclusively through the in-store Store Manager Web App today; there is no approved mobile client requirement in this release.

Decision. Route all client traffic through a single Azure API Management gateway; do not introduce a Backend-for-Frontend layer until a second client shape (e.g., a mobile app) is actually approved.

Rejected Options.

OptionWhy it lost
Build a BFF now, speculatively, for a future mobile clientNo approved mobile requirement exists; this repo's operating principle is explicit that we do not design for hypothetical future requirements

Consequences. Gains: one less container to build, deploy, and secure today. Costs: if a mobile client is approved later, introducing a BFF at that point is a scoped, known piece of follow-on work, not a redesign — the API Gateway boundary already isolates clients from internal service topology.

ADR-006 — Asynchronous Events, Not Synchronous REST, for Inventory-to-Alert Propagation

Status: Accepted

Context. A naive design would have the Inventory Command Service call the Forecasting Service directly (REST) whenever a position changes, which then calls the Alert Service directly. This chains three services' availability together for every single POS transaction.

Decision. Inventory Command Service publishes InventoryPositionChanged to the event bus using the transactional outbox pattern (DB write and event publish are atomic); Forecasting and Alert services consume independently and idempotently, keyed on event ID.

Rejected Options.

OptionWhy it lost
Direct synchronous REST chain (Command → Forecasting → Alert)Ties the availability of three services together for every transaction; a slow or down Forecasting Service would directly block inventory writes, violating the availability target in the NFR Spec
Dual-write (write to DB, then separately publish event, no outbox)Not idempotent/safe under partial failure — a crash between the DB write and the publish silently drops the event, violating this repo's non-negotiable idempotency rules

Consequences. Gains: services fail independently; a Forecasting Service outage delays forecasts, not inventory writes. Costs: requires an outbox relay process and consumer-side idempotency keys on every downstream handler — real, necessary engineering, not optional polish.
